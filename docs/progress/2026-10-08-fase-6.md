# Avance de la fase 6 — scheduler y gateways

Plan: [fase 6](../superpowers/plans/2026-10-08-fase-6-scheduler-gateways.md). Diseño de detalle:
[scheduler y gateways](../superpowers/specs/2026-10-08-fase-6-scheduler-gateways-design.md).

La implementación se hizo en la rama normal `fase-6`, creada desde `main` en
`91e95ad`. No se creó un worktree nuevo, no hubo push ni despliegue y se conservó
el directorio ajeno `.idea/`.
El 8 de octubre se integró por fast-forward local en `main` hasta `d3880ed`;
la revisión final no dejó bloqueantes y el árbol versionado quedó limpio.

El grafo `health_check` ejecuta consultas instantáneas de Prometheus, valida
umbrales y clasifica ausencia de datos, NaN y errores como `unknown`. El scheduler
registra resultados y escala anomalías en una investigación con deduplicación por
ventana. El digest diario usa zona IANA y destinos explícitos. APScheduler 3 guarda
IDs serializables en Postgres; un advisory lock permite un solo líder. El proceso
comprueba que conserva la misma sesión Postgres antes de despachar y detiene jobs
si pierde el lock. La API y `fin-graph schedules` cubren listar, crear, consultar,
actualizar, borrar y ejecutar; las escrituras exigen admin y el disparo operator.

Los jobs internos realizan retención y rechazo de aprobaciones vencidas. El rechazo
usa los locks de chat/remediación y revalida el checkpoint antes de reanudar; el
actor interno solo puede rechazar. La retención elimina también resultados de salud,
eventos de gateway y vínculos de hilos vencidos. El envío de digest conserva un
ledger durable y bloquea la repetición automática de una entrega incierta.

Slack usa Bolt con firma HTTP y Socket Mode optativo; Telegram verifica el secreto
del webhook. Ambos limitan el cuerpo, aplican canal/chat y allowlist de aprobadores,
deduplican eventos, responden antes de ejecutar la investigación y relacionan el
mensaje remoto con el hilo persistido. Publican progreso y reporte, además de
botones para aprobar o rechazar una solicitud pendiente. Las decisiones reutilizan
locks, política y auditoría de fase 5, con un advisory lock por hilo entre procesos;
la edición sigue en API/CLI. El inbox guarda el evento normalizado y redactado antes
del ack; el líder reintenta pendientes tras una caída y la alerta reutiliza un hilo
estable. La reejecución del mensaje remoto tras un crash de entrega puede dejar un
duplicado visible, pero no reejecuta automáticamente una acción mutante.

Gate local con Postgres obligatorio en `localhost:5433`: **792 pruebas aprobadas,
ninguna omitida ni bloqueada**. Ruff check/format, mypy e import-linter aprobaron.
El smoke offline completó 3 casos, 0 fallidos y 0 bloqueados; se construyó el wheel.
El wheel contiene las migraciones `0007_gateway_inbox`, `0008_gateway_attempts`
y `0009_gateway_owner`.
Las pruebas de gateway usaron ASGI/MockTransport y clientes falsos. No se llamó a
Slack, Telegram, Prometheus ni otros servicios externos reales.

La revisión independiente identificó y se corrigieron cuatro problemas: la
reconciliación cada minuto reiniciaba el próximo health check; el job de retención
omitía el purgado de metadatos auxiliares; un crash podía dejar un evento de bot
consumido sin procesar; y los locks de aprobación no cruzaban procesos. Hay
pruebas de regresión para reconciliación, retención real, replay de alertas y
botones, liderazgo único y advisory locks con dos conexiones Postgres.

La segunda revisión detectó una carrera entre worker y replay y la posible
creación de dos ejecuciones para el mismo evento. El replay ahora reclama el
evento vencido mediante actualización condicional y revoca al propietario anterior;
el fingerprint del gateway
crea un solo run de forma transaccional. Si ese run se interrumpe, se reanuda
desde su checkpoint y conserva el ID. Un fallo de entrega se reintenta hasta
cinco veces; después queda en estado `dead`, sin payload, hasta la retención.
El run conserva un heartbeat y un lock Postgres por hilo: otro proceso solo
recupera los runs abandonados. Un barrido cada minuto reconcilia los vencidos
incluso tras un reinicio rápido, con un intento de lock que no bloquea el arranque. Hay
pruebas de estas carreras con dos conexiones Postgres y de reanudación de
un checkpoint parcial o un run `queued` huérfano.
La revisión independiente final no encontró bloqueantes para el merge.

Ajustes frente al diseño base: la explicación con LLM `fast` es opcional y nunca
decide el umbral; el digest usa resultados recientes sin un modelo externo. Las
solicitudes de aprobación creadas fuera del bot se notifican con un mensaje
separado y correlacionado, porque los reportes existentes no siempre tienen una
solicitud pendiente. El líder único no realiza promoción automática de una réplica
en espera tras una caída; esa ampliación queda para fase 8. La UI de schedules
permanece en fase 7.

Pendiente de validación externa: credenciales de sandbox para verificar firmas y
Socket Mode Slack, webhook y callbacks Telegram, permisos de canales, entrega real,
consultas Prometheus y operación prolongada/reinicio del scheduler. Ningún servicio
real fue modificado. La siguiente etapa es fase 7: UI de investigaciones, chat,
schedules e integraciones sobre las rutas existentes.
