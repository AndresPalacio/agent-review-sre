# Progreso F2: integraciones de datos de mercado

Plan: transformación SRE → finanzas, fase F2.

- Estado: F2 completa y verificada, también contra Yahoo real. Sin commits.

## Diseño

Los proveedores de datos y las tools están separados:

- **Proveedores** (`yahoo`, `financial_datasets`, `market_fixtures`) implementan
  `integrations/market_data.MarketDataClient` y **no tienen tools propias**. Si cada uno publicara
  `get_prices`, los nombres chocarían en el registro.
- **`analytics`** publica todas las tools y resuelve en el `RunContext` el proveedor que nombra
  `MARKET_DATA_PROVIDER`. El modelo nunca elige proveedor. `analytics` solo se activa si su
  proveedor está activo, así que nunca ofrece tools que fallarían siempre.
- Todo es **point in time**: ningún método devuelve datos posteriores a `as_of`.

## Entrega

| Pieza | Contenido |
|---|---|
| `integrations/market_data.py` | `MarketDataClient` (prices, financial_metrics, line_items, insider_trades, company_news, market_cap), `RunMemo` (caché por corrida que une llamadas concurrentes idénticas en una sola petición y sobrevive a la cancelación de un llamador), `StaticMarketData` y `load_market_fixtures` (`<dir>/<TICKER>/*.json`) |
| `integrations/yahoo/` | Port async del `YahooProvider` de ai-hedge-fund: chart v8, quoteSummary con cookie+crumb, fundamentals-timeseries y RSS. Sesión httpx con un solo cookie jar y un cliente efímero por petición, solo hosts de Yahoo, sin redirecciones, tope de 2 MB, backoff 429 (2/5/10 s) y reinicio de cookie+crumb ante 401/403. `verify` lee precios de AAPL |
| `integrations/financial_datasets/` | Port opcional (`FINANCIAL_DATASETS_API_KEY`): filtros nativos `report_period_lte`/`filing_date_lte`, backoff 429 corto (2/5 s en vez de 60-150 s), mensaje claro ante una key rechazada y la key nunca en errores |
| `integrations/analytics/` | `AnalyticsEngine` (scores por analista/ticker/fecha con caché por corrida y `position_limits`) y 12 tools read-only: `get_prices`, `get_financial_metrics`, `search_line_items`, `get_company_news`, `get_insider_trades`, `get_market_cap` y `compute_{fundamentals,valuation,technicals,sentiment,buffett,graham}` |
| `integrations/tooling.invoke_tool` | Ejecuta una tool fuera de un agente con su `ToolRuntime`; F3 lo usa para el modo `tool_plan` |
| `integrations/base.HttpStatusError` | `IntegrationError` con el código HTTP, para reintentar 429 |
| `catalog.default_registry()` | Integraciones de mercado primero; las SRE siguen hasta F9 |
| `integrations setup` | Admite `yahoo` y `financial_datasets` |

Las tools `compute_*` devuelven como artifact el `QuantScore` completo. Esa es la evidencia citable
que `thesis_verification` ya lee para el conflicto de valoración. Al modelo le llega un resumen
compacto: señal, confianza, partes y huecos. Las de datos le resumen y guardan las filas completas
en el artifact.

### Reglas point-in-time de Yahoo (nuevas respecto al original)

- El snapshot TTM de quoteSummary describe el presente. Solo se usa si `as_of` tiene como mucho
  `YAHOO_SNAPSHOT_MAX_AGE_DAYS` (7) días; el original lo etiquetaba con cualquier fecha.
- Un estado anual cuenta como conocido `YAHOO_REPORT_LAG_DAYS` (45) días después del cierre fiscal.
- El market cap histórico es el cierre de `as_of` × las acciones actuales (aproximación documentada).
- Insiders (~1 año) y noticias (feed actual) devuelven listas cortas o vacías en fechas viejas.
  Eso es un hueco de datos, no un error.

### Errores

Un proveedor caído lanza `IntegrationError` legible y sin credenciales; el modelo lo recibe como
texto de la tool. El motor de analytics convierte cada fetch fallido en un `data_gap` y puntúa con
lo que llegó. Solo si no llegó nada y algo falló lanza el error, así un apagón sale como tool fallida
(evidencia con `error`) y no como un score vacío con apariencia de confianza.

## Corrección de seguridad encontrada

El detector SRE `ACCOUNT_ID` enmascaraba **cualquier** número de 12 dígitos. Con `MASK_ENABLED=true`
convertía `"revenue": 383000000000` o un market cap en `<ACCOUNT_ID_…>` y corrompía los datos que lee
el modelo. Ahora exige contexto AWS (un ARN o una etiqueta `account`/`account_id`); el test SRE
existente sigue pasando y hay un test nuevo para cifras financieras.
