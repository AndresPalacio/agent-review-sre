# Avance de la fase 1d

Plan: [Cloud, cambios, entrega y MCP](../superpowers/plans/2026-10-07-fase-1d-cloud-entrega-mcp.md).
Rama local `fase-1d` creada desde `main` en `1c14b6b`, en el directorio principal del
repositorio. No se usó worktree para esta fase; `.idea/` permanece sin modificar.

AWS aporta diez tools de lectura para CloudWatch Metrics/Alarms/Logs Insights, EKS,
RDS y Performance Insights, Lambda y CloudTrail. El SDK usa la cadena estándar de
credenciales y ejecuta llamadas sincrónicas fuera del event loop. Sentry aporta cinco
tools, incluido el detalle de evento con stacktrace; GitHub, cinco tools de cambios.
Los listados conservan cursor o página y las consultas temporales están acotadas.

La entrega Slack, Telegram y PagerDuty es una API explícita, separada de las tools.
`verify_all` solo lee identidad. Los reportes salientes se renderizan y redactan
antes de cada POST. El loader MCP lee JSON validado, resuelve credenciales por nombre
de variable de entorno, conecta solo servidores habilitados, aísla fallos y etiqueta
cada tool con dominio y nivel de efecto. Una tool no clasificada es `external`.
La prueba MCP de extremo a extremo inicia un servidor `stdio` local, descubre una
tool y la invoca sin red ni credenciales.

La revisión final encontró y corrigió una exposición de `Environment.Variables` en
la configuración Lambda. También abrió continuaciones para todas las lecturas AWS
que devuelven `NextToken`/`Marker`, acotó los eventos de Sentry por `start/end`,
filtró deployments GitHub por `created_at` y fijó timeout de sesión a cada llamada
MCP. Los argumentos `stdio` con flags de credenciales o cabeceras (`-H`) se
rechazan; se usan `env_vars`. GitHub no ofrece filtro temporal en el listado de
deployments: se filtra cada página localmente y se conserva `nextPage` para continuar.
Una segunda revisión ajustó `GetResourceMetrics` a 25 resultados por página, el
máximo admitido por Performance Insights; las páginas siguientes usan `NextToken`.

Decisiones de diseño: Sentry no documenta filtro temporal para releases, así que la
tool devuelve una página reciente con cursor. Slack recibe `client_msg_id` estable;
Telegram y PagerDuty no ofrecen deduplicación durable de notas/mensajes en esta capa.
La tabla de entregas de Fase 4 deberá evitar duplicados entre reinicios. MCP queda
como loader explícito; el servidor lo conectará durante su lifespan en Fase 4.

Validación externa pendiente: credenciales de solo lectura y endpoints AWS, Sentry,
GitHub, Slack, Telegram, PagerDuty y servidores MCP configurados. No se realizaron
envíos reales ni cambios de infraestructura. Estas verificaciones están bloqueadas
por falta de credenciales/servicios suministrados; no cuentan como pruebas aprobadas.

Gate local con Postgres: 535 pruebas aprobadas, ninguna omitida; Ruff, formato,
mypy e import-linter aprobados. Los tests HTTP de proveedores usan transporte
simulado y los de AWS usan clientes SDK falsos. Revisión final de código completada
y hallazgos corregidos.

El siguiente paso es la Fase 2: grafo de investigación con especialistas en paralelo
y CLI mínimo, seguido de validación con una alerta y modelo reales cuando existan.
