# Avance de la fase 5 — remediación HITL, chat y memoria

Plan: [fase 5](../superpowers/plans/2026-10-07-fase-5-hitl-chat-memoria.md).

La fase 5 se implementó en la rama normal `fase-5`, creada desde `main` en
`02d63f9`. No se creó otro worktree ni se hizo push. Se conservaron `.idea/` y
el worktree preexistente. OpenSRE sirvió como referencia funcional según el diseño;
el código usa los contratos propios de `sre-graph` y no depende de su framework.

Cierre: la revisión final quedó sin hallazgos críticos ni importantes. Los commits
`280a5e3` y `f83cca4` se integraron en `main` mediante fast-forward hasta
`f83cca4`. El gate se repitió en `main` con Postgres local obligatorio: 708 pruebas
aprobadas, ninguna omitida; Ruff, formato, mypy e import-linter aprobados.

El catálogo explícito de remediación cubre Kubernetes (scale, rollout restart,
rollout undo y delete pod), Alertmanager (crear y expirar silencio), Grafana
(anotación), Datadog (mute monitor), Sentry (resolver/ignorar issue), GitHub
(crear issue) y PagerDuty (ack/resolve). Las acciones Kubernetes se preparan con
dry-run server-side. Undo aplica un JSON Patch atómico condicionado a
`resourceVersion`; delete usa precondición de UID. La fase de aprobación acepta
approve/edit/reject con actor y rol del contexto autenticado; los argumentos
editados se preparan otra vez. La ejecución usa `@task` y un ledger durable con
clave de acción: un resultado confirmado se reutiliza y uno incierto bloquea el
reintento. La verificación de workloads hace polling acotado. Un fallo de escala
o de silencio creado propone una acción compensatoria que exige otra aprobación;
las acciones sin compensación segura informan el resultado fallido y el paso
manual.

La investigación guarda resúmenes verificados, sin transcript, en el Store y usa
recuperación acotada de incidentes previos y runbooks como referencia para
sintetizar el RCA, sin tratarlos como evidencia citable. La memoria busca por
metadatos cuando no hay embeddings; `EMBEDDINGS_PROVIDER=openai` activa un índice
semántico opcional en Postgres. Los incidentes recurrentes conservan IDs de corrida
distintos y el fingerprint como metadato. El chat mantiene los mensajes en el
checkpointer y usa notas redactadas, runbooks/skills de ID exacto y especialistas
de lectura. Incorpora middleware de límites, resumen, edición de
contexto, tareas, retries, fallback configurable, cache, redacción, evidencia y
aprobación de herramientas mutantes. La API ofrece chat SSE, aprobación con roles
y remediación explícita. `ask`/`chat` ofrecen REPL local con SQLite o modo remoto
con API key y HTTPS obligatorio fuera de loopback.

Los grafos de investigación, chat y remediación usan identidades internas de
checkpoint separadas. La investigación iniciada desde chat bloquea explícitamente
la herencia del checkpointer. La retención de servidor sigue también la actividad
de chat/remediación, revalida la antigüedad bajo locks y elimina los tres espacios
de checkpoint. Las decisiones de aprobación se auditan con actor, tipo, herramienta
y hash de argumentos, sin persistir los argumentos crudos. Los resultados de
acciones se asocian a su hilo para eliminarlos solo al vencer ese hilo. El chat
permite recuperar solicitudes pendientes por API y con `/resume`. En el CLI, los claims
de acciones usan SQLite transaccional incluso entre procesos.

Pruebas offline cubren approve/edit/reject, doble reanudación y resultado incierto,
rollback, errores y precondiciones de Kubernetes, rutas de mutación por vendor con
MockTransport, memoria, chat, API ASGI y CLI local/remoto. Gate completo con
Postgres local obligatorio en `localhost:5433`: **708 pruebas aprobadas, ninguna
omitida**; Ruff, formato, mypy e import-linter aprobados. Evaluación smoke local:
**3 completadas, 0 fallidas, 0 bloqueadas**. No se llamaron servicios externos
ni se ejecutaron mutaciones reales. El wheel se construyó y contiene las
migraciones nuevas, el chat y su middleware.

Ajustes frente al diseño: las mutaciones se agrupan en `ActionCatalog` y no se
publican como tools directas de cada integración; el chat expone una única tool
de remediación que vuelve a preparar el destino tras HITL. El SSE de chat emite
mensajes y solicitudes de aprobación, no fragmentos de token. La búsqueda
semántica queda optativa; su configuración tiene pruebas offline, pero no se
ejecutó contra un proveedor de embeddings real.
La expiración automática de aprobaciones depende del scheduler de fase 6.

Pendiente de validación externa: credenciales y modelos reales, permisos de
escritura específicos de cada vendor, exactitud de los payloads frente a sus
servicios, operación de larga duración del servidor y recuperación tras reinicio
con integraciones reales. No hubo despliegue ni modificación de infraestructura.
