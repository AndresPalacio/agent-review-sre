La consola React/Vite/TypeScript/Tailwind consume la API existente. Incluye
investigaciones con timeline SSE, hipótesis, evidencia e informe; chat con
recuperación por ID; catálogo y preparación de remediaciones; revisión de acciones
con approve/edit/reject; automatizaciones health_check/digest e integraciones.
Las operaciones siguen los roles viewer/operator/approver/admin del servidor.

La API key permanece en memoria. Las peticiones y streams usan X-API-Key sobre
fetch; cerrar sesión cancela peticiones activas. No se incluyen secretos en el
build, la URL ni el almacenamiento del navegador. React renderiza el contenido
como texto. La API añade historial público de chat y snapshots de investigación
saneados, sin exponer mensajes de herramientas ni credenciales.

Cada tarjeta de aprobación envía los IDs de los interrupts mostrados. El servidor
los compara bajo los locks existentes antes de auditar o ejecutar; una solicitud
obsoleta devuelve 409. El contrato es aditivo: API/CLI anteriores pueden omitir
approval_ids. El rollback genera una nueva aprobación. El RCA sigue siendo de
lectura y no convierte recomendaciones narrativas en comandos.

Vite compila a server/static. FastAPI sirve assets y rutas SPA explícitas sin
capturar endpoints de API, salud o documentación; archivos ausentes y traversal
devuelven 404. Docker compila primero la UI y después instala Python; el wheel
incluye los estáticos generados. CI ejecuta las verificaciones web y comprueba su
presencia dentro del wheel. Consultar [README](../../README.md#consola-web) para
desarrollo, build y pruebas.

## Aceptación

La prueba de navegador usa FixtureBackend del escenario EKS OOMKilled, tools y
grafos LangGraph reales, un modelo guionado y una acción local simulada. Verifica
investigación con evidencia → preparación sin escritura → aprobación con una sola
ejecución y auditoría; un segundo intento devuelve 409. También cubre rechazo,
viewer sin mutaciones, clave sólo en memoria, chat/historial, CRUD de schedules e
integraciones sin configurar.

El fixture está exclusivamente en tests/web: ignora configuración ambiental de
modelos y servidor, no tiene clientes de proveedores ni fallback de LLM, escucha
en loopback y elimina su base temporal al terminar. Su endpoint de inspección no
forma parte del servidor de producción. Las pruebas de aislamiento fuerzan
configuración ambiental inválida y un fallo de construcción para comprobar que
se libera SQLite incluso en Windows.

La prueba SSE interrumpe deliberadamente el primer stream y comprueba reintento,
Last-Event-ID y la misma cantidad de eventos que el historial, sin duplicados.
Se inspeccionaron capturas de investigación, aprobación, chat y programaciones,
incluyendo móvil de 390 × 844. El timeline tiene altura acotada, el informe presenta
conclusiones y respaldo, las citas enlazan evidencia y los datos técnicos completos
se pueden desplegar. Las capturas locales están en web/test-results/visual-*.png.

La revisión independiente quedó sin bloqueantes. Se corrigieron configuración
ambiental y cierre de SQLite del fixture, IDs repetidos al quitar/añadir checks,
errores de recarga tras aprobación obsoleta y carreras al cambiar de hilo durante
peticiones. Las regresiones cubren esos casos, sesiones en memoria, cancelación,
aprobación de múltiples acciones, edición y presentación de incertidumbre.

## Alcance de la validación

Las pruebas offline verifican conexión entre superficies, control humano,
persistencia y contratos. No miden la calidad del RCA con un modelo real ni
validan credenciales, permisos o cambios en proveedores externos. Las pruebas de
carga, el fan-out SSE multi-réplica y el wizard de integraciones pertenecen a fase 8.

Se conservan los cambios del cierre de fase 6 en la misma rama local
fix/cierre-fase-6. No se ha realizado commit, push ni despliegue.
